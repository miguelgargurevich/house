# Contrato de API (backend nuevo)

Lo implementa la rama `feat/backend-seguro`. El frontend se construye contra esto.
Autenticación: sesión de servidor con la cookie `house_sesion` (httpOnly, SameSite=Lax; el navegador la manda sola, `api()` usa `credentials: 'same-origin'`). **Ya no existe `Authorization: Bearer` ni token en `localStorage`.** Toda mutación (POST/PUT/PATCH/DELETE) exige además el header `X-CSRF-Token` (se obtiene en login y `/me`, `api()` lo guarda solo en memoria) y un `Origin`/`Referer` propio; si falta → 403. Errores: `{ error: 'mensaje' }` con el status HTTP.
Login: `POST /api/auth/login` {email,password} → `{user, csrf}` + `Set-Cookie: house_sesion`; `GET /api/auth/me` → usuario + `csrf` (401 = sin sesión). Vigencia 12 h absolutas / 2 h de inactividad.
Sesiones: `POST /api/auth/logout` → 204 (revoca y borra la cookie); `GET /api/auth/sesiones` → `[{id, ip, user_agent, creada, ultimo_uso, actual}]` (solo las mías y activas); `DELETE /api/auth/sesiones/:id` → 204 (404 si no es mía); `POST /api/auth/sesiones/cerrar-otras` → `{cerradas}`. `PUT /api/me/password` revoca las demás sesiones; cambiar el rol/contraseña de un usuario o eliminarlo cierra las suyas.
Montos (`Decimal`) llegan como string: usa `soles()` / `Number()`.

- Todas las listas devuelven `{items, total, page, pageSize}` con query `?page=1&pageSize=20&q=texto&orden=campo:asc|desc` (pageSize máx 100; `q` busca en nombre/código/email/descripcion según recurso). Recursos: usuarios, empresas, complejos, pisos, estructuras, unidades, conceptos, recibos, pagos, tareas, auditoria. Los GET por id devuelven el objeto. POST→201 con el objeto creado; PUT/PATCH→objeto actualizado; DELETE→204.
- Rutas CRUD (mismos nombres de hoy): /api/usuarios, /api/empresas, /api/complejos, /api/pisos, /api/estructuras, /api/unidades, /api/conceptos, /api/recibos, /api/pagos, /api/recibo-conceptos, /api/recibo-concepto-unidades; NUEVA /api/tareas (TareaMantenimiento) con `PATCH /api/tareas/:id/estado` {estado: pendiente|en_progreso|completada}. Las listas de unidades incluyen `propietario:{id,nombre}`, `inquilino:{id,nombre}`, `complejo:{id,nombre}`; las de recibos incluyen `complejo`, `totales:{monto, cobrado, pendiente}` (calculados) y `estado`; las de usuarios incluyen `empresa:{id,nombre}`.
- Inquilino↔unidad: añade `inquilino_id Int?` a Unidad (relación "InquilinoUnidad" con Usuario) y actualiza el seed para asignar cada inquilino a una unidad distinta de las de su complejo. Tras cambiar el esquema ejecuta `npx prisma db push` contra la base local y vuelve a sembrar con una BD vacía (para eso crea una BD nueva `house_dev2` en el mismo Postgres o usa el esquema por defecto; NO uses `prisma migrate reset` ni `db push --force-reset` sobre la base `house` principal).
- Perfil: `PUT /api/me` {nombre, telefono}; `PUT /api/me/password` {actual, nueva} (verifica la actual, mínimo 8).
- Residentes: `GET /api/me/unidades` (propietario: sus unidades; inquilino: la suya) con complejo; `GET /api/me/cargos?estado=pendiente|pagado|vencido&page=` → cargos (ReciboConceptoUnidad) de SUS unidades con `{id, monto, estado_pago, estado (pagado|pendiente|vencido, calculado por fecha_vencimiento del recibo), concepto:{nombre}, recibo:{id,mes,anio,descripcion,fecha_vencimiento}, unidad:{id,codigo}, pagos:[…]}`; `GET /api/me/cargos/:id`; `GET /api/me/pagos` (pagos de sus cargos); `POST /api/me/cargos/:id/pagos` {metodo_pago: transferencia|yape|plin|efectivo|tarjeta, referencia?, observaciones?} registra un Pago por el monto del cargo, marca estado_pago='pagado' y fecha_pago, rechaza si ya está pagado o no es suyo (404).
- `GET /api/dashboard/resumen` según rol. admin/superadmin: `{recibos_emitidos, cargos_pendientes_monto, cobrado_mes, morosos (unidades con cargos vencidos), unidades_total, tareas_abiertas, cobrado_por_mes:[{mes:'2026-05', emitido, cobrado} (últimos 6)], estados:{pagado,pendiente,vencido}}` (superadmin: global + `empresas_total`, `usuarios_total`; admin: su empresa). propietario/inquilino: `{deuda_total, vencidos, proximo_vencimiento:{cargo_id,monto,fecha}|null, pagado_ano}`. mantenimiento: `{tareas_pendientes, en_progreso, completadas}`. seguridad: `{unidades_complejo, complejo}`.
- `GET /api/reportes/morosidad` (admin/superadmin): lista de unidades con deuda vencida: `[{unidad, propietario, deuda_total, cargos_vencidos, dias_max_atraso}]`, paginada igual que las demás.


## Adiciones (obligatorias en el backend; el frontend ya las usa)
- `GET /api/usuarios` acepta también `?rol=propietario|inquilino|…` y `?empresa_id=` (sólo superadmin puede filtrar por otra empresa).
- `GET /api/recibo-concepto-unidades` (cargos) acepta `?estado=pendiente|pagado|vencido&q=<código de unidad>`; cada fila incluye `unidad:{id,codigo}`, `concepto:{nombre}` (vía reciboConcepto), `recibo:{id,mes,anio,fecha_vencimiento}`, `estado` calculado.
- `POST /api/recibos` acepta `{complejo_id, mes, anio, fecha_emision, fecha_vencimiento, descripcion?, conceptos:[{concepto_id, monto, es_recargo?}]}` y genera los `ReciboConcepto` más un `ReciboConceptoUnidad` por cada unidad activa del complejo (con el mismo monto). `GET /api/recibos/:id` devuelve además `conceptos:[…]` y `cargos:[{id, unidad:{id,codigo}, concepto:{nombre}, monto, estado}]`.
- `GET /api/unidades?complejo_id=&estado=`, `GET /api/pagos?metodo_pago=`, `GET /api/tareas?estado=&asignado_id=` filtran en servidor.
- **Avisos** (`/api/notificaciones`, admin y superadmin; el admin solo ve los de su empresa, otro tenant → 404). `GET /api/notificaciones?estado=pendiente|enviada|error|omitida&canal=email|whatsapp&tipo=recibo_emitido|por_vencer|vencido|pago_validado|pago_rechazado&q=` (q busca en asunto y destinatario; `orden` por `id|created_at|programada_para|enviada_at|estado|canal|tipo`) → lista paginada de `{id, usuario:{id,nombre}, canal, tipo, estado, asunto, intentos, error, programada_para, enviada_at, ref_entidad, ref_id, created_at}` (sin `cuerpo`). `GET /api/notificaciones/resumen` → `{pendiente, enviada, error, omitida}` (conteos). `GET /api/notificaciones/canales` → `{email:{configurado, faltan:[nombres de variables]}, whatsapp:{…}}`, nunca valores. `POST /api/notificaciones/:id/reenviar` (solo `error`/`omitida`, si no 409) → el aviso en `pendiente` con `intentos 0`; auditado.
- **Preferencias de avisos** (cualquier rol): `GET /api/me/avisos` y `PUT /api/me/avisos` {aviso_email: bool, aviso_whatsapp: bool, telefono?: string|null} → `{aviso_email, aviso_whatsapp, telefono}`. `telefono` omitido = no se toca; `''`/null = se borra; texto = celular peruano (9 dígitos que empiecen con 9, con o sin +51; se guarda como `+51 987 654 321`) o 422. Activar WhatsApp sin celular → 422. `GET /api/auth/me` suma `aviso_email` y `aviso_whatsapp`.
- **Disparadores de avisos**: `POST /api/recibos` encola un `recibo_emitido` por usuario (propietario e inquilino de las unidades con cargo) y canal; un fallo al encolar no deshace la emisión. Backend para otras funciones: `encolarAviso(tipo, usuarioId, {entidad:'cargo'|'recibo', id})` en `src/server/services/avisos` (para `pago_validado`/`pago_rechazado` pasa `{entidad:'cargo', id: <ReciboConceptoUnidad.id>}`; idempotente, respeta preferencias y devuelve cuántas notificaciones creó).
- `GET /api/pagos` incluye `unidad:{codigo}`, `concepto:{nombre}`, `usuario:{nombre}`.
- `GET /api/empresas/:id` y `PUT /api/empresas/:id` los puede usar el admin sobre SU empresa.

## Comprobantes de pago y su validación
- **Estados**: `ReciboConceptoUnidad.estado_pago` admite `en_revision` (el residente pagó y falta validar). El campo calculado `estado` de un cargo es `pagado|pendiente|vencido|en_revision`; un cargo en revisión nunca es `vencido`. `GET /api/me/cargos`, `GET /api/recibo-concepto-unidades` aceptan `?estado=en_revision`.
- **Pago** suma `estado_validacion` (`por_validar|validado|rechazado`, `validado` por defecto), `validado_por_id`, `validado_at`, `motivo_rechazo`; las listas de pagos incluyen `comprobante:{id,nombre,tipo_mime,tamano,created_at}|null` (nunca los bytes) y `validado_por:{id,nombre}`. `GET /api/pagos?estado_validacion=` filtra.
- `POST /api/me/cargos/:id/pagos` (residente) → pago `por_validar` y cargo `en_revision` (409 si ya está pagado o en revisión). `POST /api/pagos` (admin) → pago `validado` y cargo `pagado` (409 si el cargo tiene un pago en revisión).
- `POST /api/pagos/:id/comprobante`: cuerpo CRUDO (no JSON), `Content-Type` image/jpeg|image/png|image/webp|application/pdf, máx. 2 MB (413), `X-Nombre-Archivo` opcional (URL-encoded). Se verifican los bytes mágicos (422 si no corresponden al tipo; 415 si el tipo no está permitido; 422 si está vacío). Responde 201 `{id,pago_id,nombre,tipo_mime,tamano,sha256,created_at}`; reemplaza el anterior. Puede subirlo quien registró el pago mientras esté `por_validar` (después 409) o un admin de la empresa/superadmin.
- `GET /api/pagos/:id/comprobante`: entrega el archivo (`Content-Type` guardado, `Content-Disposition: inline; filename=…; filename*=UTF-8''…`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, `Cache-Control: private, no-store`). Lo ven el admin de la empresa del pago, el superadmin y los residentes (propietario o inquilino) de la unidad del pago. Otro tenant o ajeno → 404; mantenimiento y seguridad → 403.
- `PATCH /api/pagos/:id/validacion` (admin/superadmin) `{estado:'validado'}` o `{estado:'rechazado', motivo (3–300)}` → pago actualizado. Validado: cargo `pagado` con `fecha_pago`; rechazado: cargo `pendiente` y el motivo queda en el pago (el residente lo ve en `GET /api/me/cargos`, `pagos[0].motivo_rechazo`). Sólo se revisa un pago `por_validar` (409 si ya fue revisado).
- **Totales**: `en_revision` cuenta en «por cobrar» (`cargos_pendientes_monto`, `totales.pendiente`, `deuda_total` del residente) pero no en `cobrado_mes`/`cobrado_por_mes`/`pagado_ano` (sólo pagos `validado`) ni en morosidad (`morosos`, `estados.vencido`, `/api/reportes/morosidad`, `estado_cobranza`). Nuevos campos: dashboard admin `estados.en_revision` y `pagos_por_validar`; dashboard residente `en_revision`; `totales.en_revision` en recibos.


## Medios de pago del block y cargo de junta
No hay pasarela: el vecino paga por fuera (cuenta bancaria o Yape/Plin con QR que define la junta de su block) y luego registra el pago con su comprobante (flujo «En revisión» → validación de arriba).
- **Cargo en la junta**: `Usuario.cargo_junta` (`presidente|tesorero|secretario|vocal`, sólo rol propietario) y `Usuario.estructura_id` (block del cargo; null = todo su condominio `complejo_id`). `POST/PUT /api/usuarios` los aceptan (sólo admin/superadmin): un cargo exige rol propietario y `complejo_id`; el block debe ser de ese condominio y de la empresa del admin (422); sin cargo no hay block; quien deja de ser propietario pierde el cargo. Cambiar `cargo_junta`, `complejo_id`, `estructura_id` (o el rol) revoca las sesiones del usuario. `POST /api/auth/login` y `GET /api/auth/me` suman `cargo_junta` y `estructura_id` (`/me` ya traía `complejo`).
- **Quién es «junta»**: propietario con cargo `presidente` o `tesorero` y `complejo_id`. Secretario y vocal no ganan permisos. **Ámbito**: unidades/medios/pagos con `complejo_id` igual al del cargo y, si el cargo tiene `estructura_id`, ese mismo block. Una junta sin block alcanza todos los blocks de su condominio y los medios de «todo el condominio»; una junta de un block NO gestiona los medios de «todo el condominio» (`estructura_id` null). Regla en `src/server/lib/junta.ts`.
- **Pagos para la junta**: `GET /api/pagos` y `GET /api/pagos/:id` (con `?estado_validacion=`), `GET /api/pagos/:id/comprobante` y `PATCH /api/pagos/:id/validacion` valen también para la junta, sólo sobre pagos de unidades de su ámbito (fuera → 404; secretario, vocal y propietario sin cargo → 403). **No** puede `POST/PUT/DELETE /api/pagos`, emitir recibos ni administrar usuarios (403), y no puede validar un pago registrado por ella misma (403).
- **`/api/medios-pago`** (admin de su empresa, superadmin, junta en su ámbito; otro rol → 403; ámbito ajeno → 404). Un medio: `{id, complejo_id, estructura_id, tipo: banco|yape|plin, banco, tipo_cuenta, numero_cuenta, cci, titular, documento_titular, celular, qr_nombre, qr_tipo_mime, tiene_qr, activo, orden, creado_por_id, created_at, updated_at, complejo:{id,nombre}, estructura:{id,nombre}|null}`; los bytes del QR nunca salen en JSON.
  - `GET /` `?complejo_id=&estructura_id=<id|ninguna>&activo=true|false` (+ paginación habitual), por `orden` y `id`. `GET /ambitos` → `{complejos:[{id,nombre,estructuras:[{id,nombre}]}], fijo}` (los condominios/blocks donde puede gestionar; `fijo` = junta de un block).
  - `POST /` `{tipo, titular, complejo_id?, estructura_id?, orden?, activo?, …}`; para la junta `complejo_id` y `estructura_id` salen de su ámbito si se omiten (`estructura_id: null` explícito = todo el condominio). `PUT /:id` (el ámbito no cambia), `PATCH /:id` `{activo?, orden?}`, `DELETE /:id` → 204.
  - Validación: **banco** → `banco` ∈ BCP, BBVA, Interbank, Scotiabank, Banco de la Nación, Mibanco, BanBif, Pichincha, Otro; `tipo_cuenta` ahorros|corriente; `numero_cuenta` 8–20 dígitos/guiones (≥ 8 dígitos); `cci` opcional de 20 dígitos; `documento_titular` opcional DNI 8 o RUC 11. **yape/plin** → `celular` de 9 dígitos que empieza en 9 (se aceptan espacios). `titular` obligatorio. Máximo **6 medios activos** por ámbito (condominio+block; 422 al crear, reactivar o activar el 7.º). Lo que no aplica al tipo se guarda en null.
  - **QR**: `PUT /:id/qr` cuerpo CRUDO `image/png|jpeg|webp` (máx. 500 KB → 413; 415 otro tipo; 422 vacío o bytes que no corresponden al tipo), `X-Nombre-Archivo` opcional; `DELETE /:id/qr` → 204; `GET /:id/qr` entrega la imagen (nosniff, `Content-Security-Policy: sandbox`, `Cache-Control: private, no-store`) al admin de la empresa, la junta del ámbito y los residentes (propietario o inquilino) de unidades del ámbito del medio, **sólo si el medio está activo** para ellos; otro caso → 404 (mantenimiento y seguridad → 403).
- **Residente**: `GET /api/me/medios-pago?cargo_id=` (obligatorio; cargo ajeno → 404) → array de los medios ACTIVOS de la unidad del cargo: primero los de su block y luego los de todo el condominio, cada grupo por `orden`. Cada uno: `{id, tipo, ambito: 'block'|'condominio', banco, tipo_cuenta, numero_cuenta, cci, titular, celular, tiene_qr, orden}` (sin `creado_por_id` ni documento del titular). Sin medios → `[]`.
- Auditoría (entidad `medio-pago`): `crear`, `editar`, `eliminar`, `subir_qr`, `quitar_qr` con `{tipo, complejo_id, estructura_id, ultimos4}`; nunca el número completo, el CCI, el celular ni el QR.
